**Verified by the Planner (2026-09-27; read-only over `ssh umbrel`, the Umbrel's own umbreld source, Docker Hub's public API):**
- **umbreld pulls every image at install and at update.** `App.install()` and `App.update()` call `pull()` (`modules/apps/app.ts`), which runs `docker pull` on every compose image through dockerode (`modules/utilities/docker-pull.ts`); the legacy `post-patch-update` script step also runs `compose pull`. An image that exists only after a local `docker build` cannot install: it must be in a registry the daemon can pull from (D112).
- **Docker treats `127.0.0.0/8` as an insecure (HTTP) registry by default** (`docker info` → `InsecureRegistryCIDRs` `127.0.0.0/8`, `::1/128`; no `daemon.json`), so a registry bound to `127.0.0.1` needs no TLS. Docker 28.5, Compose v5.3.1, buildx 0.35 (BuildKit), storage driver `overlay2` (the classic image store), x86_64, 8 cores.
- **umbreld removes every container at every start of umbreld** (`Apps.cleanDockerState()`: `docker stop` + `docker rm` of `docker ps -aq`, called from `index.ts` on start outside development mode). Images and bind-mounted folders survive; a standalone registry container **does not survive an Umbrel reboot**, whatever its restart policy. App containers are re-created by umbreld from local images at boot (no pull when the image is present). Consequence: the registry runs as its own store app, which umbreld starts at every boot (§7.3; owner question 1 keeps the plain-container fallback).
- **Install copies the app folder; update copies only a whitelist.** Install rsyncs the store's app folder into `~/umbrel/app-data/<app-id>/` (`--archive`, `--exclude .gitkeep`, no `--delete`), so a `data/` skeleton of `.gitkeep` files becomes folders owned by uid 1000 before the first start (the sibling `tenon-joinr-backup` app relies on it). An update copies only `docker-compose.yml`, `*.template`, `exports.sh`, `torrc`, `hooks` and then `umbrel-app.yml` (`legacy-compat/app-script`, `pre-patch-update`): **an update never touches `data/`.** Uninstall deletes the whole app-data folder without asking (D113; the store README's warning).
- **Ports:** every `port:` in every `umbrel-app.yml` of the four app stores on the device, and every current TCP listener, were read. **4930 and 4932 are free** in both lists (4931 is the sibling `tenon-joinr-backup`). Chosen: **app port 4932**, **loopback registry port 4930** (§7.3). The stores refresh every few minutes, so the scripts re-check before every release (§7.4, §7.6).
- **The build's download hosts are reachable from the Umbrel** (27/09/2026): `cdn.sheetjs.com` (the SheetJS tarball, HTTP 200), `registry.npmjs.org` (200), Docker Hub's registry (`/v2/` answers 401, i.e. reachable). Memory: 15 GiB (about 4 GiB available), plenty for the web build.

**Verified in the plan revision (2026-09-27, read-only, umbreld source and the device):**
- **Umbrel's Stop and Restart remove the app's containers.** `App.stop()` and `App.restart()` call the legacy `app-script stop`, which runs `compose rm --force --stop`; `restart` is `stop` then `start`. After a Stop in the UI, `docker inspect tenon-joinr-finance_app_1` finds **no such object** (§7.6 handles it).
- **The update order is destructive before the pull.** `App.update()` runs `pre-patch-update` (stop = remove the containers; copy `docker-compose.yml`; an EXIT trap copies `umbrel-app.yml`, i.e. the new version), **then** `pull()`. A pull failure leaves the app stopped, its manifest already at the new version (Umbrel offers no Update to retry) and a compose naming an image that is not on the host. Hence the registry as a store app (§7.3, owner question 1).
- **`umbreld` rewrites the app-data compose with js-yaml** (`patchComposeFile`, forcing `container_name: <id>_<service>_1`); `yq` is installed on the host (`/usr/bin/yq`), as are `curl`, `nice` and `ionice`.
- **Every app's default network is the shared external `umbrel_main_network`** (`legacy-compat/docker-compose.common.yml`), so any container of any installed app can reach `tenon-joinr-finance_app_1:3001` directly, without the Umbrel login (§7.7 isolates the app).
- **app_proxy is optional per app** (`app-script` adds `docker-compose.app_proxy.yml` only when the compose defines `app_proxy`), so a UI-less app (the registry, §7.3) is valid.
- **umbrelOS 1.7.4 has built-in Backups** (`modules/backups`: Kopia snapshots of the umbrel data folder, app-data included, on an interval, while apps run) and honours a manifest **`backupIgnore`** list (paths relative to the app-data folder, `[-a-zA-Z0-9._/*]` only; used by many official apps).
- **Browsers send `Sec-Fetch-*` headers only to potentially trustworthy origins** (HTTPS or localhost). The app is reached over plain HTTP (`http://umbrel:4932`), so in production the header never arrives (§5.8 adds an Origin rule).
- **Runtime egress:** the server calls `query1.finance.yahoo.com` and `api.coingecko.com` (no separate FX host); they leave from a container through Docker DNS (checked in the live smoke, §9).
- **Memory:** `MemAvailable` about 4.2 GiB of 15 GiB with the owner's other apps running (§7.2 guards the build).
- **The scheduler** inserts the `job_runs` row as `running` **before** `job.run` and stores `err.message` of a thrown job as `error`; `job.run` is called synchronously inside the run's async body, before `inFlight` is set (§5.3, §5.4).
- **`.prettierignore` holds `**/*.md`**: Markdown docs are never format-checked. The Vite dev proxy uses `changeOrigin: true` (it rewrites `Host` to the API port). `e2e/import.spec.ts` runs a committed re-import inside the read-only desktop and phone projects (it writes a pre-import backup). `ColumnTable` has a sticky first column and a horizontal-scroll wrapper, but no sticky header or max height. `useHashTarget` in Settings fires when the settings query resolves. The import CLI's usage text names `pnpm import:workbook`.

Details, including host facts, paths and the demo specifics, are in `docs/private/stage-7-private.md`.

## 1. Overview & flow

### 1.1 What Stage 7 delivers
1. **Backups** (server, §5): a nightly backup at **02:30 server-local** (D115) with a start-up catch-up, verified consistent copies (`VACUUM INTO` + `integrity_check` on the copy before it is kept), retention of **14 daily + the newest copy of each of the last 12 months**, a separate set per kind (10 pre-import, 10 by hand, 5 pre-restore, 5 pre-update), `job_runs` recording, failure retries, and a layout a later rsync to the NAS can copy as is (D111).
2. **Backups API** (§4): list with kind, time and size; "Back up now"; download of one file (strict name validation, no path traversal).
3. **Restore** (§5.5): a CLI shipped in the image (`node dist/cli/restore.js <backup>`) that validates the file (integrity, lineage, migration level not newer than the app), takes a pre-restore backup (or, with `--force`, sets a damaged live file aside raw) and swaps the database while the app is stopped; a documented step list and a wrapper the coordinator runs from the dev PC, which also restores a backup file kept on the PC (the reinstall case, D113).
4. **Start-up safety** (§5.7): a pre-update backup before a start applies migrations, and a refusal to start on a database a newer version has migrated.
5. **Web** (§6): a dense Settings "Backups" section (list, back up now, download, last and next run, retention text, the uninstall warning), an "About" block (app and server versions, database level, time zone), a stale-backup callout, phone width.
6. **Deploy** (§7): a pinned, TZ-checked Dockerfile; the CLIs in the image; `tools/deploy/*` Node scripts run from the Windows dev PC (ship the build context, build on the Umbrel, push to the loopback registry, write `tag@digest` into the store, a smoke run on the host); the registry as a second store app `tenon-joinr-registry/` (owner question 1; the plain-container `ensure` script stays as the bootstrap and fallback); the store's `tenon-joinr-finance/` folder (the app on a private network with app_proxy) and README update (local, uncommitted); `docs/deploy/RUNBOOK.md`.
7. **Cutover** (§9, the coordinator at the demo, D116): a fresh Drive export imported on the deployed app, reconciled, auto-record switched on (D84), any missing month recorded or skipped (D94); the PLAN acceptance (two PCs and a phone, persistence across restarts, a live restore, clean reconciliation).
8. **CODE-7 cleanup** (Stage 6 deferral): drop `sumCents`/`sumDecimalStrings`, drop `STAGE_TITLES`/`PageDef.stage` (§5.9, §6.6).

All routes under `/api`, JSON unless stated, `cache-control: no-store`, the Stage 0 error shape `{ error: { code, message } }`. Times are ISO 8601 **with the server's local offset** (e.g. `2030-03-15T02:30:00+11:00`), as the recorder's `nextRunAt`.

### 4.1 Error codes
| Code | Status | When |
|---|---|---|

```ts
export interface BackupScheduleDto {

}

export interface BackupsResponse {
  backups: BackupFileDto[];                  // every kind, newest first
  totalBytes: number;
  freeBytes: number | null;                  // statfs of DATA_DIR; null when unavailable
  schedule: BackupScheduleDto;
  running: boolean;                          // a backup job is in flight
  lastRun: JobRunSummary | null;             // the newest `backup` job run (any trigger)
  lastBackupAt: string | null;               // the newest nightly or manual file's createdAt
  stale: boolean;                            // §5.4
  retention: typeof BACKUP_RETENTION;
  app: {
    version: string;                         // APP_VERSION
    migrations: number;                      // applied migrations
    restoredFrom: { name: string; at: string } | null;   // app_meta restore.last (§5.5 step 10)
  };
}

  backup: BackupFileDto;
  joined: boolean;             // true when the click joined a backup already in flight

```
The `backup` job's `job_runs.detail`: `{ kind, name?, slot?: string /* the settled slot, local ISO */, sizeBytes?, durationMs?, verified?, pruned?: string[], skipped?: 'import_in_progress' | 'empty' | 'not_due', reason?: 'no_space' | 'verify_failed' | 'io', attempt?: number }`. **The page reads** `lastRun.status`, `lastRun.error` (always one of the three category messages of §4.1, never raw text) and `lastRun.detail.skipped` (frozen): `running` → pending badge "Running"; `succeeded` without `skipped` → go "Succeeded"; `succeeded` or `partial` with `skipped` → pending "Skipped" plus a muted reason ("nothing to back up yet" for `empty`, "an import was running" for `import_in_progress`); `failed` → failed badge plus the category message.

**`keptAs` in the list (frozen rule):** `retain(nightlyFiles, 'nightly', ref)` with `ref` = the newest **non-future** nightly file's instant (the instant of the last prune, so every nightly file on disk is in the keep map and the value matches what was actually kept), else `now`. Future files get `'future'`. A nightly file absent from the keep map (only possible when a prune could not delete it, §5.3) is listed as `'recent'`. The fixture-consistency test uses the same reference.

## 5. Server spec (server-backups)

### 5.1 Configuration
`NIGHTLY_BACKUPS` (`true|false|1|0|yes|no`) → `Config.nightlyBackups: boolean`; default **true**, and **false under `NODE_ENV=test`** (as `TEST_DEFAULTS`). Off means no timer and no start-up catch-up; "Back up now", pre-import, pre-restore and pre-update backups still work. The schedule time, the retention and the stale threshold are constants (§3.2), not settings. **`PUBLIC_PORT`** (digits, optional; unset by default; the store compose sets `4932`) → `Config.publicPort: number | null`, used only by the write guard's Origin rule (§5.8). No other new variable. The README's configuration table gains the row (deploy writes the README).

### 5.2 Files and names (`src/backups/names.ts`)
- **Folder:** `<DATA_DIR>/backups/`, flat (no sub-folders), the Stage 1 folder. Every file the app keeps there matches `BACKUP_FILE_NAME_RE`; anything else (a file the owner dropped in, a Stage 1–6 folder such as a hand-made `pre-stage6-<date>/`) is **never listed, never pruned, never deleted**.
- **Names:** `<kind>-YYYYMMDD-HHmmss±HHMM.db` in **server-local time with its offset** (e.g. `nightly-20300315-023000+1100.db`), so the two 02:30s of the April change get different names and every name sorts and parses to one instant. **Every kind, pre-import included, is written with the offset** from Stage 7 on. The legacy Stage 1 form `pre-import-YYYYMMDD-HHmmss.db` (no offset) still lists and prunes: parsed as local time, the earlier instant when ambiguous (the only place that rule applies). A collision in the same second adds `-2`, `-3`, … (as Stage 1).
- **The local date and month of a file** are the `YYYYMMDD` / `YYYYMM` written in its name (the server-local date when the copy was made, which is what the owner sees), not a re-computation in the process's zone; retention groups by them (§5.3), so it does not depend on the process TZ.
- **Order:** by the parsed instant, then the suffix. `createdAt` in the DTO is that instant written with its offset.
- **Writing (all kinds):** the copy is written to a hidden temporary `.<final name>.partial` in the same folder, verified, fsynced, then **renamed** to the final name (atomic), and the folder fsynced (skipped where the platform refuses, i.e. Windows). A listed file is therefore always complete and verified; a later rsync with `--exclude '.*'` never copies a partial. **Leftover cleanup** (at service start and at the restore CLI's start; one process owns the folder): delete every `.*.partial*` file in `backups/` (the partial and any `-wal`/`-shm`/`-journal` sidecar the verification left) and every `.finance.db.restoring*` file in `DATA_DIR`. Hidden **folders** (`.unverified-pre-restore-*`, §5.5) and anything else are never touched.
- **Immutability:** a kept file is never modified; retention only deletes.

### 5.3 The verified copy and retention (`src/backups/copy.ts`, `src/backups/retention.ts`)
**`writeVerifiedBackup(database, dataDir, kind, now, { jobRunId?, slot?, copy? })`** (used by every kind, including pre-import, §11 item 1):
1. **Space check:** `fs.statfsSync(dataDir)` free bytes ≥ 2 × (the size of `finance.db` + `finance.db-wal`) + 64 MiB, else throw `BackupError('no_space')`. (statfs unavailable → skip the check.)
2. `VACUUM INTO ?` (a **bound parameter**) on the live connection, through the injectable `copy` seam (default: the synchronous `VACUUM INTO`; tests pass an async fake that resolves on demand, §5.4). A consistent snapshot even while other statements run; synchronous, so nothing else in the process runs meanwhile.
3. **Make the copy self-consistent**, on a second, read-write connection to the temporary file: `PRAGMA journal_mode = DELETE` (a self-contained single file, no sidecars); delete `app_meta` `server.running_since`; when `jobRunId` is given, set that `job_runs` row (the backup's own run, which the scheduler inserted as `running` before the job ran) to `succeeded` with `finished_at` = the backup instant and `detail` naming the file (and `slot`); any **other** row left `running` in the copy becomes `failed` with error `interrupted` (what `markInterruptedRuns` would do after a restore). So a restored copy never shows "Last run: Failed" for its own backup.
4. **Verify** on the same connection: `PRAGMA integrity_check` returns exactly one row `ok`, the `__drizzle_migrations` row count equals the live database's, and `app_meta` holds `created_at`; close. Any failure → delete the temporary file (and its sidecars), throw `BackupError('verify_failed')`.
5. `fsync` the file, rename to the final name, fsync the folder; return `{ name, path, sizeBytes, durationMs }`. An `fs` or SQLite error in any step → `BackupError('io')` (the raw error is logged by the caller with its `code` only, never its message or a path).
6. **Prune only after a verified copy**: the kind's own set, never another kind's. A failed backup therefore never reduces what is kept. **A delete that fails** (`EBUSY`/`EPERM`, e.g. a download streaming the file on Windows) is logged (code and file name) and skipped; it never fails the run; the next prune retries.

**Retention (pure, `retain(files, kind, ref: { instant: Date; localDate: string /* YYYYMMDD, from the service */ }) → { keep: Map<name, BackupKeptAs>; remove: string[]; future: string[] }`):**
- **Future files** (instant > `ref.instant` + `BACKUP_FUTURE_TOLERANCE_MS`: a copy taken while the clock was wrong, a clock change, a file copied in by hand) are not inputs: never removed, reported in `future` (the list shows `'future'`; the service logs the names once per run).
- **nightly:** group the nightly files by the **local date written in their name**; the newest file of each date is that date's copy (older ones on the same date are removed). **Daily:** keep the copies of the **14 newest dates** that have one (not the 14 calendar days before `now`, so an outage never eats the dailies). **Monthly:** for each calendar month from `ref.localDate`'s month back **11 months** (12 in all), keep the newest nightly file whose name's month is that month, if any. A file kept by both rules is `daily_and_monthly`. Everything else nightly is removed.
- **manual, pre-import, pre-restore, pre-migrate:** keep the newest `BACKUP_KEEP_BY_KIND[kind]` by instant (`recent`); remove the rest.
- A file that does not match the name rule is not an input (never removed).
- **The monthly copy is "the newest copy dated in the month"** (D115 as worded). It is taken at 02:30 on the month's last day, before that day's 23:00 month-end record (D89), so a month's own recorded snapshot first appears in the next month's copies; nothing is lost (every later copy holds it). Decided; no change to D115.

**Worked examples** (nightly, one copy a day at 02:30; `now` just after that day's run):
| # | Situation | Kept (daily) | Kept (monthly, besides the dailies) | Total |
|---|---|---|---|---|
| A | Daily copies 01/01/2030 → 15/09/2030; now 15/09/2030 | 02/09 … 15/09 (14) | 31/01, 28/02, 31/03, 30/04, 31/05, 30/06, 31/07, 31/08 (Oct–Dec 2029 have none; September's newest is the 15/09 daily → `daily_and_monthly`) | 22 |
| B | As A, one year on: daily copies to 15/09/2031 | 02/09/2031 … 15/09/2031 | 31/10/2030 … 31/08/2031 (11 month-ends; Sep 2031 is the daily) | 25 |
| C | As A, but the server was off 04/09 → 13/09; started 14/09 at 10:00 (catch-up copy at 10:02, §5.4) and ran 15/09 at 02:30 | 15/09, 14/09 (10:02), 03/09, 02/09, 01/09, 31/08 … 23/08 (14 dates, reaching back over the gap) | 31/01 … 31/07 (31/08 is a daily) | 21 |
| D | Two nightly copies on 15/09 (a start-up catch-up at 02:05 because the 14/09 copy was missing, then the 02:30 run) | 15/09 keeps **02:30** only; the 02:05 copy is removed at that prune | — | — |
| E | The first nightly ever | that one | — (it is also this month's newest → `daily_and_monthly`) | 1 |

Example B's arithmetic: the window is Oct 2030 → Sep 2031; the September 2030 copies all fall out; the 31/08/2031 month-end is kept as August's newest (monthly) because it is not among the 14 newest dates.

### 5.4 The nightly job (`src/backups/service.ts`)
**Shape** (as the Stage 5 recorder): a `BackupService` with its own timer on the injectable `Clock`, registering one scheduler job **`backup`** with `intervalMs: 0` (manual-only in the scheduler; the service decides when), so every run writes a `job_runs` row with its trigger (`schedule`, `startup`, `manual`) and joins a run in flight.
```ts
export interface BackupService {
  start(): void;                         // registers the job, deletes stale partials, arms the start-up check
  stop(): Promise<void>;                 // clears the timer, waits for an in-flight run
  backupNow(): Promise<{ file: BackupFileDto; joined: boolean }>;
  status(): { enabled: boolean; nextRunAt: string | null; running: boolean; lastRun: JobRunSummary | null };
}
```
Decorated as `app.backups`; `index.ts` starts it after `app.recorder.start()`; `preClose` stops it before the recorder and the scheduler.

**The slot.** `slot(date) = new Date(y, m, d, 2, 30)` in server-local time. On the October change 02:30 does not exist and the slot is **03:30 AEDT** (the engine's gap rule, verified); on the April change the slot is the **first** 02:30 (AEDT). `S(now)` = the latest slot ≤ `now` (today's if `now ≥ slot(today)`, else yesterday's).

**Due rule.** A nightly run is due when `enabled`, and the slot `S(now)` is **not settled**. `S` is settled when (a) a nightly file has an instant in **[`S(now)`, `now` + `BACKUP_DUE_SLACK_MS`]** (a file dated further ahead never suppresses a run), or (b) a `succeeded` `backup` run in `job_runs` has `detail.slot` equal to `S(now)` (this covers the empty-database skip and a restart after the run), or (c) this process has given up on it (`doneSlot`, after 3 failed attempts, below). So:
- The server running across 02:30 → one run at the slot.
- **Start-up catch-up (decision):** at start, after `BACKUP_STARTUP_DELAY_MS` (2 min, after the recorder's 60 s first check), the same rule is evaluated; if the last slot passed while the server was down, **one** backup is taken then (trigger `startup`, named with the actual time, counted as that local date's copy). Never more than one, however many slots were missed. *Why:* the same reasoning as D82 (a missed month is caught up at the next start): an Umbrel reboot or an app update across 02:30 would otherwise leave a hole in the dailies; one `VACUUM INTO` of a few MB costs nothing; and nothing is ever back-dated (the name is the real time).
- April: after the 02:30 AEDT run, the second 02:30 (AEST) finds a file with an instant ≥ `S` → not due. October: one run at 03:30 AEDT.
- **Nothing to back up:** when `hasDomainData` and `hasAppData` are both false (a fresh install before the first import), the run records `succeeded` with `skipped: 'empty'` and `detail.slot = S` (no file). "Back up now" still copies an empty database when asked.
- **A clock that jumps backwards** (by a day, say): the newest file is now ahead of `now` by more than the slack, so it does not settle `S(now)`; one run is taken at the (re-lived) slot, named with the real (earlier) time. Tested.

**Timer.** `planNext(now, state)` (pure, unit-tested) → `wakeAt = min(slot after now, now + BACKUP_WAKE_MAX_MS (6 h), retryAt, catchUpAt)`; the 6 h cap keeps the timer correct across DST changes, clock corrections and `setTimeout`'s limit (as `SNAPSHOT_WAKE_MAX_MS`). **`nextRunAt`** for the status is the timer's **actual next due run**: `min(retryAt, catchUpAt, next slot ≥ now)` (a pending 15-min retry or an armed 2-min start-up catch-up shows as such), local ISO with offset (`localIsoWithOffset`, reused from the recorder); null when disabled. Tested in both states.

**Failure and retry.** The `backup` job's `run()` **catches everything itself** and returns `{ status: 'failed', error: <one of the three category messages of §4.1>, detail: { reason: 'no_space' | 'verify_failed' | 'io', … } }`; it logs the raw error at error level with `err.code` only (no message, no path). So `job_runs.error`, the 500 body and `lastRun.error` never carry a path or raw SQLite text. Retry after **15 min**; at most **3 attempts per slot** (then `doneSlot = S` and it waits for the next slot; the stale flag and the page show it). `import_in_progress` (the import lock is held at the start of a run) → `partial` with `skipped: 'import_in_progress'`, retry after 15 min, **not counted** as an attempt. `markInterruptedRuns` (existing) marks a `backup` run left `running` by a crash as failed at the next start.

**`backupNow()`** calls `scheduler.run('backup', 'manual')`, which never throws the job's error; it maps a `failed` result to `throw new BackupError(detail.reason)` and a `partial` import skip to `ImportInProgressError`; the route maps them to 500 `BACKUP_FAILED` (`expose: true`, the category message) and 409. Test: a `copy` seam throws an error whose message contains a path; neither `job_runs.error`, the 500 body nor `GET /api/backups`'s `lastRun.error` contains it.

**Concurrency.**
- **The import lock:** a nightly run skips while it is held (above); "Back up now" answers **409 `IMPORT_IN_PROGRESS`**; the upload route's own pre-import backup runs inside the lock (unchanged, now through `writeVerifiedBackup`). Because `VACUUM INTO`, the verification and the prune are synchronous, a backup and an import (one synchronous transaction) can never interleave inside the process; the lock rule only avoids backing up in the middle of an upload's steps.
- **The recorder:** no shared mutex is needed (a record's write is synchronous too, and 02:30 never meets 23:00); nothing waits on the recorder.
- **Manual vs nightly:** both go through the one `backup` job: a click during the nightly run **joins** it (`joined: true`, the nightly file is returned); a nightly slot reached during a manual run joins the manual run, and **counts** for the slot only if the file's kind is nightly — otherwise the due rule fires again after it finishes. Kind = `manual` when the trigger is `manual`, else `nightly`. **In production a join cannot happen today**: the default `copy` is synchronous, so `job.run` finishes before `scheduler.run` registers the run as in flight (verified in `scheduler/index.ts`); `joined` becomes reachable only if an async step is added later. The join tests use the async `copy` seam (§5.3 step 2).
- **Stop:** `stop()` waits for the in-flight run (the copy is synchronous, so a run is never half-written; a SIGTERM during it waits for it).

**Stale.** `stale = enabled && hasDomainData && ref !== null && now − ref > 48 h`, where `ref` = the newest **non-future** nightly or manual file's instant, else the first **committed** import run's start (so a fresh install is not stale before its first night). A missing `backups/` folder counts as no files. `/api/status` carries `{ stale, lastBackupAt }`.

### 5.5 Restore (`src/backups/restore.ts`, `src/cli/restore.ts`)
**Usage:** `node dist/cli/restore.js <backup> [--yes] [--force] [--json]` in the image; `pnpm restore:backup <backup> [--yes] [--force]` in a checkout. `<backup>` is a **bare name** (resolved in `<DATA_DIR>/backups/`, validated with `BACKUP_FILE_NAME_RE`; a leading `BACKUP_DOWNLOAD_PREFIX` is stripped first, so a downloaded file's name works too) **or a path** to a SQLite file (a downloaded backup copied in by hand, or the wrapper's upload, §7.6; any name). No prompts (it runs in a one-off container): without `--yes` it prints what it would do and exits 3.

**Exit codes:** `0` restored · `1` failed (nothing changed, or the pre-restore backup is named) · `2` usage or configuration · `3` confirmation required (`--yes`) · `5` the backup is not valid (integrity, not a Joinr database, a different lineage, newer than this app, or a WAL-mode file with its `-wal` beside it) · `6` the app looks running (`--force` overrides the marker only, never the lock check).

**Every read of the live database before `--yes` is `readonly: true`** (so closing it never checkpoints the WAL and changes `finance.db`'s bytes); the refusal tests hash `finance.db` **and** `finance.db-wal` when present.

**Steps** (each tested):
1. `loadConfig`; the leftover cleanup of §5.2; resolve the file; refuse the live `finance.db` itself (same real path) and anything that is not a regular file (exit 2).
2. **Validate the candidate.** A **path** candidate is first checked for WAL mode: header bytes 18 and 19 both `2` and a `<path>-wal` sibling present → exit 5 "This file is a live database with unsaved changes beside it: checkpoint it first, or restore a backup file". A path candidate is then **copied to a temporary file** (in `DATA_DIR`, hidden, removed on exit) and validated there, so opening it never needs to create sidecars next to the original. On a read-only connection (`fileMustExist`): the 16-byte header `SQLite format 3\0`; `PRAGMA integrity_check` = `ok`; `app_meta.created_at` exists (a Joinr database); `__drizzle_migrations` exists with `m_b` rows, **`m_b ≤ m_app`** (the app's journal entry count; newer → exit 5 "This backup was made by a newer version of the app (database level m_b; this app knows m_app). Install that version or newer, then restore."), and **the first `m_b` rows' `created_at` equal the journal's first `m_b` `when` values** (same lineage; else exit 5).
3. **The app must be stopped:** open the live database **read-only** and read `app_meta` `server.running_since` (§5.8); set → exit 6 "The app appears to be running (or did not shut down cleanly). Stop the app; if it is stopped, re-run with --force." (`--force` skips this check only.) A live file that cannot be opened skips the marker (reported in the summary). A missing live database (a fresh folder) skips steps 3–5.
4. **Summary** (always printed; with `--json` a JSON object): the backup's name, instant, size, database level, the live database's level and its last import and newest recorded month (dates and counts only, no figures; "cannot be read" for a damaged live file). Without `--yes` → exit 3.
5. **Lock check (after `--yes`, ignores `--force`):** a fresh connection with `busy_timeout 0` tries `PRAGMA locking_mode = EXCLUSIVE` then `BEGIN EXCLUSIVE`; `SQLITE_BUSY` → exit 6 "Another process has the database open". POSIX locks hold across containers on one host filesystem. **The test must prove it** with a second, open and idle connection in WAL mode (the server's pattern); if SQLite grants the lock anyway, server-backups drops this step, keeps the marker and the wrapper's container check, and writes a Scaffold note.
6. **Pre-restore backup:** `writeVerifiedBackup(live, dataDir, 'pre-restore', now)` + prune to 5; then `PRAGMA wal_checkpoint(TRUNCATE)` and close the live connection. **Damaged live file:** if the live file cannot be opened, or its verified copy fails (`verify_failed`, `io`), then **with `--force`** the raw `finance.db`, `finance.db-wal` and `finance.db-shm` are **moved** into `<DATA_DIR>/backups/.unverified-pre-restore-<utc stamp>/` (hidden, so never listed, pruned or rsynced), the checkpoint is skipped, the summary names the folder, and the restore continues at step 7 (no sidecars remain for step 8 to delete); **without `--force`** → exit 1 "The current database could not be backed up (it may be damaged). Re-run with --force to set it aside unverified and restore." (`no_space` always exits 1.) Test: a truncated live `finance.db` restores with `--force`, and the raw copy exists.
7. **Stage the new file:** copy the candidate to `<DATA_DIR>/.finance.db.restoring`, fsync, re-run `integrity_check` on the copy.
8. **Swap:** delete `finance.db-wal` and `finance.db-shm` (empty after the checkpoint), rename `.finance.db.restoring` → `finance.db` (atomic replace), fsync the folder.
9. **Post-check:** open the new `finance.db`, `integrity_check` = `ok`.
10. **Markers in the restored database:** set `restore.last` = `{"name": <backup name or basename>, "at": <now ISO>}` (the About block shows it); delete `server.running_since` (Stage 7 copies never hold it, §5.3, but a path candidate or a legacy pre-import copy may).
11. Print "Restored <name>. The pre-restore copy is backups/<name>. Start the app." and, when `m_b < m_app`, "The app will update the database from level m_b to m_app when it starts (a pre-update backup is taken first)." Exit 0.
On any failure after step 6 the live `finance.db` is either untouched (before step 8) or the new file (after it); the message names the pre-restore backup (or the unverified folder) to restore back to.

**After a restore:** the server's next start runs pending migrations (with the §5.7 backup), marks interrupted runs, re-arms the recorder (its catch-up applies to the restored snapshots, D82/D94) and the backup service. The restored database's `job_runs` show the backup's history, which is correct.

### 5.7 Start-up safety (`src/backups/migrate.ts`, `index.ts`, `cli/import.ts`)
`migrateWithBackup(database, config, now)` replaces the bare `runMigrations` call in `index.ts` and `cli/import.ts`:
- `applied` = `countAppliedMigrations`, `known` = the journal's entry count.
- **`applied > known` → refuse to start** (exit 1): "This database was updated by a newer version of Joinr Finance (level applied; this version knows known). Install that version or newer, or restore a backup made before the update." Nothing is written.
- **`0 < applied < known` → a `pre-migrate` backup first** (`writeVerifiedBackup`, prune to 5), logged with the two levels, then `runMigrations`. A fresh database (`applied = 0`) migrates without a backup.
- The log line never includes a path or a figure.
- **The import CLI refuses to run while the app runs** (D34's override in a one-off container would otherwise bypass the in-process import lock and leave the running app's caches stale): `server.running_since` set (read-only open) → exit 6 with the restore CLI's message, unless `--force`. ### 5.8 The running marker and the cross-site write guard
- **`server.running_since`:** set in **`app.ts` with Fastify's `onListen` hook** (ISO now) and deleted in `onClose` just before `closeDatabase` (not in `index.ts`, which runs `main()` on import and so cannot be reached in process). A test: `buildApp` → `app.listen({ port: 0 })` → marker set → `app.close()` → marker gone; a crash leaves it (the CLI's `--force` path). `BuildAppOptions` gains `backupClock?: Clock` (like `recorderClock`) for the service tests, and `backupCopy?` for the `copy` seam.
- **Cross-site guard** (`src/security.ts`, registered first in `buildApp`): an `onRequest` hook on `/api/*` for `POST`, `PUT`, `PATCH`, `DELETE`:
  1. `sec-fetch-site` present → allowed only when `same-origin` or `none`; anything else → **403 `CROSS_SITE_REQUEST`** ("Requests from another site are refused").
  2. `sec-fetch-site` absent (**the production case**: browsers send Fetch Metadata only to HTTPS or localhost origins, and the app is served over plain HTTP) and an **`Origin`** header present (`Origin: null` is always refused) → allowed only when the Origin's `host:port` (default port filled in) equals the request's `Host`, or its `X-Forwarded-Host` (with `X-Forwarded-Port` when given), or — when `config.publicPort` is set — the Origin's port equals `publicPort`; outside production (`NODE_ENV !== 'production'`) a loopback Origin (`localhost`, `127.0.0.1`, `[::1]`, any port) is also allowed, because the Vite proxy's `changeOrigin: true` rewrites `Host` to the API port. Otherwise 403.
  3. Neither header (curl, `app.inject`, Playwright's `request`, the CLIs) → allowed.
  The `publicPort` form exists because it is not yet known whether Umbrel's app_proxy preserves `Host` or sets `X-Forwarded-Host`; the store compose sets `PUBLIC_PORT: 4932`, so the owner's own pages pass either way, while another Umbrel app (same host, **another port**, which counts as same-site so the Umbrel cookie is sent) is refused. A cross-site page on another host is refused by rule 2 (its Origin differs in host). A refusal logs the method and the three header values (`sec-fetch-site`, `origin`, `host`), never a path or a query. Tests: each method × each `Sec-Fetch-Site` value; GET never blocked; Origin from another port on the same host → 403; the same host:port → pass; `X-Forwarded-Host` match → pass; `publicPort` match → pass and mismatch → 403; the dev-proxy case (loopback Origin, rewritten Host, non-production) → pass, and the same in production → 403; `Origin: null` → 403; no headers → pass; the error shape. The live check through app_proxy is §9 step 6.

- **Registry first:** `registry.mjs ensure` runs before anything is built (in `app` mode a check only: the Joinr Registry app must be running; in `container` mode it starts the container).
- **Guard first:** the guard must exit 0 before anything is shipped (it scans the same set). It is run as `spawn(process.execPath, [<tsx cli resolved with require.resolve('tsx/cli')>, 'tools/privacy-guard/src/cli.ts', '--all'])` — **never `spawn('pnpm', …)`** or a `.cmd` shim, which fail on Windows (`ENOENT`, and `EINVAL` for a `.cmd` without a shell since the CVE-2024-27980 fix).
- **Memory guard:** before building, read `MemAvailable` from the host's `/proc/meminfo`; below **2.5 GiB** → exit 5 "Not enough free memory on the Umbrel to build safely" (`--force-build` overrides).
- **Transfer:** `git archive --format=tar <tree>` piped into `ssh <host> -- 'mkdir -p <dir> && tar -x -C <dir>'`, with `<dir>` = `<home>/joinr-build/<version>-<tree first 12>` on the Umbrel (outside app-data and the Samba share). `.gitattributes` (`* text=auto eol=lf`) makes the archive LF. The dev PC needs no Docker and no SMB mapping.
- **Build and push on the host:** `docker build --provenance=false --build-arg APP_VERSION=<v> --build-arg APP_REVISION=<tree> -t 127.0.0.1:<port>/joinr-finance:<v> <dir>` then `docker push`, then `docker inspect --format '{{json .RepoDigests}}'` → the `sha256:` digest; cross-checked with the registry's `Docker-Content-Digest` header for the tag (`curl -sI` with the manifest `Accept` types, on the host). No `nice`/`ionice`: they would only lower the docker CLI client, not the daemon's BuildKit workers; the memory guard and `NODE_OPTIONS` are the bounds.
- **Tags are immutable:** before building, if the registry already has `joinr-finance:<v>`: with **`--reuse-existing`** and the existing image's `org.opencontainers.image.revision` label equal to the tree being shipped → skip the build and push, reuse its digest and only write the store (the case where the push succeeded and a later step failed); otherwise → exit 4 "Version <v> is already in the registry: bump the version in package.json". A **failed build pushes nothing, so the version stays free** (no bump needed to retry).
- **`--prerelease <id>`** (`^[0-9A-Za-z.]+$`, e.g. `rc.1`; only with `--skip-store`): tags and labels the image `<v>-<id>` and passes `APP_VERSION=<v>-<id>` (the version regex allows it), without touching `package.json`; used by the live smoke (§9 step S).
- **Old contexts:** keep the newest 3 build folders under `<home>/joinr-build`; the remote listing is **filtered** to names matching `^\d+\.\d+\.\d+(-[0-9A-Za-z.]+)?-[0-9a-f]{12}$` and each older folder is removed with `rm -rf -- '<home>/joinr-build/<validated name>'`; anything else in the folder is ignored (a test plants `..`, `*`, a name with a space and a name with a quote, and asserts none reaches `rm`).

### 7.3 Registry (default: the `tenon-joinr-registry` store app; fallback: a plain container) — `tools/deploy/registry.mjs ensure | status`
**Why it matters (verified, §header):** an Update clicked while the registry is down stops and removes the app's containers, copies the new compose, marks the manifest with the new version, and only then fails the pull: the app stays stopped, Umbrel offers no Update to retry, and after a reboot a plain registry container is gone. The owner clicks Update in the UI, often long after a release and possibly after a reboot. So the default (owner question 1, **(b)**) is a registry that umbreld itself starts at every boot.

**(b) Default — the store app `tenon-joinr-registry/`** (deploy writes it into the local store clone, uncommitted, in the sibling's commented style):
- `umbrel-app.yml`: `manifestVersion: 1`, `id: tenon-joinr-registry` (permanent), `name: Joinr Registry`, `category: developer`, `version: '2.8.3'` (the image's; its own bump rule), `port: 4930` (the host-only registry port, so no other app can take it; there is no web UI and the Open button leads nowhere, which the description says), a description (what it is: the host-only image registry the owner's self-built apps install from; **⚠️ uninstalling it deletes the stored images: Joinr Finance keeps running, but its next Update or a reinstall fails until a new version is released**), `backupIgnore: ['data/*']` (the images are rebuildable and large), every other required field as the sibling's.
- `docker-compose.yml`: **no `app_proxy`** (valid, §header; nothing is served to the LAN); one service `registry`: `image: registry:2.8.3@sha256:<digest>` (tag and digest), `restart: on-failure`, `user: '1000:1000'`, `ports: ['127.0.0.1:4930:5000']` (**loopback only**), `volumes: ['${APP_DATA_DIR}/data:/var/lib/registry']`, `environment: { REGISTRY_STORAGE_DELETE_ENABLED: 'false' }`. Delete stays **off**: the unauthenticated loopback API is reachable by any host-network container, and deleting a pinned manifest would break the next Update or a reinstall; offline garbage collection works without it. `data/.gitkeep` skeleton (uid 1000). `icon.svg` in the same style as the Joinr Finance icon with the label "REGISTRY".
- **Order of first use (§9):** the store is pushed first with `tenon-joinr-registry/` only (and the README), the owner installs it, then the live smoke and the release push into it, then the store gets `tenon-joinr-finance/`.

**`registry.mjs`** (`JOINR_REGISTRY_MODE` = `app` (default) | `container`):
- **`ensure`** in `app` mode (read-only on the host): the container `tenon-joinr-registry_registry_1` is running and `curl -fsS http://127.0.0.1:4930/v2/` on the host answers 200 → OK; otherwise exit 3 "Start (or install) the Joinr Registry app in Umbrel" (it never starts an app's container behind umbreld).
- **`ensure`** in `container` mode (the fallback (a), and a bootstrap if the owner prefers it): container **`joinr-registry`**, `registry:2.8.3@sha256:<digest>`, `-p 127.0.0.1:4930:5000`, `--restart always`, **`--user 1000:1000`**, `-v <home>/joinr-registry:/var/lib/registry` (an **absolute** path from the resolved remote home; the folder is created first with `mkdir -p` as the `umbrel` user, so nothing under the home is ever root-owned and cleanup never needs sudo), no delete. Running → OK; exists but stopped → `docker start`; missing → `docker run -d …`; then the `/v2/` check and `docker port joinr-registry` must show only `127.0.0.1:4930`. Refuses (exit 3) when 4930 is bound by anything else. Tests assert the absolute path and `--user` in the command.
- **`status`**: the mode, the container's state, image and bindings, the tags of `joinr-finance` (`/v2/joinr-finance/tags/list`), storage size, and (§7.6) whether the store's pinned digest is present.
- **With (a) only**, the failure mode is stated honestly in §12 and the RUNBOOK: after any Umbrel reboot, run `pnpm umbrel:registry ensure` before clicking Update or Install; if an Update already failed, run `ensure` and then Umbrel → Restart (never a reboot, which removes the registry again).

### 7.4 Writing the store (`release.mjs`, the last step; never commits)
- `JOINR_STORE_DIR` (default `../tenon-umbrel-store`, a sibling of the repo) must be a git work tree holding `tenon-joinr-finance/`.
- **Before writing, two host checks (read-only), else exit 2 and nothing written:** (1) the pinned manifest exists in the registry: `curl -fsSI -H 'Accept: application/vnd.docker.distribution.manifest.v2+json, application/vnd.oci.image.manifest.v1+json, application/vnd.oci.image.index.v1+json, application/vnd.docker.distribution.manifest.list.v2+json' http://127.0.0.1:4930/v2/joinr-finance/manifests/sha256:<digest>` answers 200; (2) **ports**: `grep -h '^port:' <home>/umbrel/app-stores/*/*/umbrel-app.yml` over every store **except** the `tenon-joinr-finance` and `tenon-joinr-registry` folders shows neither 4932 nor 4930, and `ss -ltnH` shows no listener on 4932 and none on 4930 other than the registry's `127.0.0.1:4930` (the stores refresh every few minutes, so a later app could take a port).
- `docker-compose.yml`: replace the one line matching `^\s*image:\s*127\.0\.0\.1:\d+/joinr-finance:\S+@sha256:[0-9a-f]{64}\s*$` with `    image: 127.0.0.1:4930/joinr-finance:<v>@sha256:<digest>` (exactly one match, else exit 2).
- `umbrel-app.yml`: replace `^version: '[^']*'$` with `version: '<v>'` (exactly one match).
- **The bump rule, enforced:** if the manifest already says `<v>` and the compose pins a **different** digest → exit 4 "The image changed but the version did not: bump the version (Umbrel only offers an update when `version:` changes)". Same version and same digest → "Nothing to change".
- Prints: the image reference, the digest, `git -C <store> diff --stat`, a reminder that `releaseNotes:` must describe this version, and the next steps (store review → owner OK → commit and push by the coordinator → `pnpm umbrel:status` prints "Safe to click Update" → Update in Umbrel).
- `--dry-run`: prints every command it would run (git, ssh, docker) and every file change, runs nothing remote, writes nothing. `--skip-store`: build and push only.

### 7.5 Versions (one source of truth)
- The root `package.json` **`version`** is the app version everywhere: `/api/health`, the web footer and About (via `__APP_VERSION__`), the image tag, the image label, and the store manifest's **`version:`**. The deploy implementer sets it to **`1.0.0`** (the first deployed version; decided, §14 preamble). `apps/server/package.json`'s own `version` is not used and is left alone.
- **Every release that changes the image bumps the version** (semver: patch for fixes, minor for features, major for a data change that needs a restore to go back). The registry refuses to overwrite a tag (§7.2) and the store writer refuses a new digest without a new version (§7.4).
- **Rollback** = a new version whose compose pins the **older image's digest** (the registry keeps every tag), plus, when the newer version migrated the database, a restore of the `pre-migrate` backup taken by the update (§5.7). The order (RUNBOOK): publish the rollback version → Update in Umbrel → **expect a crash loop** (the older image refuses the newer database, exit 1, and `restart: on-failure` restarts it) → `pnpm umbrel:restore <pre-migrate name> --stop` (restore-remote treats `restarting` as running, so `--stop` is needed) → the app comes up healthy → check `/api/health` and About. The older image's CLI can restore a pre-migrate copy (its level is ≤ the older app's; tested in §5.11).

## 11. Behaviour changes in Stage 7 (owner can veto)
Numbering is stable. No template (spreadsheet) fixes this stage.

6. **CODE-7:** the unused server sum helpers and the stage titles are removed (no visible change).
7. **The auto-record help text** no longer mentions a stage.
8. **The app runs on a private Docker network** that only Umbrel's app proxy joins (§7.7; owner question 3), so other Umbrel apps cannot call its API directly.
9. **Backup times show in the server's time zone** (Australia/Melbourne) on every device, matching the schedule and the file names.
